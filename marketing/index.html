The problem

Fuzzy RAG can't promise a citation is real

General-purpose corpus retrieval is tuned for recall over prose. Point it at statute text and it inherits three failure modes that are fine for a blog post and disqualifying for a tax filing.

General-purpose corpus retrieval
  • Chunker rebuilds text with words.join(' ') — any whitespace change breaks the source match
  • Chunks are relocated with indexOf(chunkText), silently falling back to the top of the document on a miss
  • start_char / end_char are placeholders, not verified offsets
  • The contextual embedding step runs an LLM paraphrase between the query and the statute — a hallucination surface you can't cite
MOTaxIntelligence
  • Parent = the whole statute section, stored verbatim — the only thing ever cited
  • Children are embedding windows carrying parent_id + real, invariant-checked offsets
  • Read path resolves child → parent by foreign key, never by text search — a mid-section hit still returns the exact whole section
  • A deterministic breadcrumb (RSMo Chapter 143 § 143.436 (2)) enriches the embedding — never an LLM sentence between a query and a statute
How it works

A corpus only ships if it's perfect

Each stage refuses to proceed on any defect. There is no partial, "mostly right" corpus — the pipeline fails loudly instead.

01 · fetch

Fetch

Pulls raw statute HTML from the Missouri Revisor of Statutes, a Justia mirror, and DOR guidance pages. Archives provenance and a raw-byte checksum with every page.

02 · build

Build corpus

Parses each section to a verbatim body, classifies it against a human-authored entity map, and chunks parent/child with exact character offsets.

03 · verify

Verify

The flawlessness gate: exits non-zero on any drift, coverage gap, untagged section, or checksum mismatch. Nothing ships past this line broken.

04 · ingest

Ingest

Embeds every child in-Worker with the same bge-large-en-v1.5 model Atlas uses, and writes parents + children into D1 and Vectorize together.

Operational discipline

Trust isn't a claim — it's a cron job

A corpus that was correct at ingest can still drift. Two maintenance passes run weekly and on demand, and log every result — even a clean pass — so a silently broken check is impossible.

✓

Integrity re-check

Re-verifies the parent/child no-drift invariant against what's actually stored in D1 right now — catching a partial ingest or write bug the local build never saw.

↻

Source-drift detection

Re-fetches every plain-fetchable source already in the corpus and compares a fresh checksum against the one recorded at fetch time. A mismatch means the law changed since the last pull.

▤

Append-only audit log

Every maintenance pass — clean or not — writes to ingestion_event. Row counts, retrieval date range, and recent events are all readable via a stats endpoint.

⊘

No silent auto-reingest

Drift detection only ever detects and logs. Writing a new body always goes back through the local build → verify pipeline, preserving "a corpus only ships if it's perfect."

⇄

Drop-in for Atlas

Same embedding model, same 1024 dimensions as Atlas's own corpus index. Bind this Worker as a service and query it directly — no re-embedding, no format translation.

⛭

No LLM in the read path

Retrieval is embed → vector search → parent lookup. Nothing rewrites, summarizes, or paraphrases the statute between your query and the answer.

FAQ

Questions worth asking before you trust a citation

Does the API ever paraphrase or summarize a statute?

No. The retrieval path is embed → vector search → parent lookup by foreign key. What's returned is the verbatim section body, exactly as fetched, with no LLM step in between the query and the answer.

How do you know the returned text actually matches the source?

Every parent section carries a SHA-256 checksum computed at fetch time. A weekly (and on-demand) job re-fetches every plain-fetchable source and compares a fresh checksum — a mismatch means the underlying law changed since the last pull, and it's logged, not silently absorbed.

What happens when the source law changes?

Drift detection only ever detects and logs — it never auto-reingests. A new body always goes through the full local build → verify pipeline, so a corpus update only ships once it passes every invariant check again.

Can I filter by entity type — LLC vs. S-corp?

Yes. Every request accepts an entity parameter — llc_single, llc_multi, s_corp, or general — resolved against a curated, human-authored entity map, not a keyword guess.

How does this integrate with an existing agent platform?

The recommended path is a Cloudflare Worker service binding — your platform binds this Worker and calls its /query endpoint directly. It shares the same embedding model and vector dimensionality as Atlas's own corpus index, so no re-embedding step is needed if you'd rather query the index directly.

Is coverage limited to Missouri?

Today, yes — the corpus covers Missouri income-tax statutes (RSMo Chapter 143), the LLC Act (Ch. 347), corporations (Ch. 351), and DOR guidance. Additional states are scoped per Enterprise contract; the pipeline architecture is state-agnostic by design.
